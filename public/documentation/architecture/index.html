Architecture Hexagonal / Ports & Adapters

One import in src/config.js selects the active institution. Everything else — semester structure, gen-ed grid, co-op rules, course catalog URL, disclaimers — flows from that one file through a chain of contracts (ports), implementations (adapters), context providers, and out to every component via usePort(). Nothing in core or data has institution-specific knowledge.

The one file to change
src/config.js — swap the adapter import to fork for a new institution
The seam
src/ports/ — JSDoc interface contracts between institution logic and app logic
Core invariant
No file under src/core/ or src/data/ imports from src/adapters/

The three invariants

These rules must hold for the architecture to deliver its promise. Breaking any one means forking for a new institution will require touching core logic.

#InvariantVerify with
1 core/ has zero adapter imports. No file under src/core/ may import from src/adapters/**. When a core function needs institution config, the caller passes it as an explicit parameter. grep -r "from.*adapters" src/core/ → zero results
2 data/ has zero adapter and React imports. Data modules receive ports and storage prefixes as explicit function parameters — they never call usePort(). grep -r "usePort\|useInstitution" src/data/ → zero results
3 UI components get institution config only through usePort(). No component imports from src/adapters/** directly. grep -r "from.*adapters" src/ui/ → zero results

How each layer uses institution config

ThemeContext — reads the adapter object at the module level

ThemeProvider receives storagePrefix as a React prop read from institutionAdapter.institution.storagePrefix directly. It does not call usePort() — it reads the plain JavaScript object before any React context exists. This is why ThemeProvider is the outermost provider in App.jsx.

PlannerContext — reads four ports via usePort()

// src/context/PlannerContext.jsx
const institution   = usePort(IInstitution);   // storagePrefix for localStorage keys
const calendar      = usePort(ICalendar);      // semester types → SEMESTERS grid
const courseCatalog = usePort(ICourseCatalog); // fetchAll() → course data
const specialTerms  = usePort(ISpecialTerms);  // types → span maps, drop validation

// Institution config passed as explicit params — never imported inside functions
const courses = await courseCatalog.fetchAll();   // adapter owns fetch strategy
loadSaved(institution.storagePrefix);             // storage key prefix from adapter

Weight-based span arithmetic

The single most important cross-cutting mechanic. Both ICalendar semester types and ISpecialTerms duration descriptors carry a weight on the same numeric scale. One rule covers all institution-specific span configurations:

ℹ
Span rule: A special term occupies the next consecutive semester slot when termWeight > semSlotWeight. specialTermUtils.termSpans(termWeight, semSlotWeight) is the single site where this rule lives — no hardcoded duration checks anywhere in core logic.
Term typetermWeightDropped onsemSlotWeightSpans?
Co-op 6-mo2.0Fall / Spring1.0Yes — occupies drop + next slot
Co-op 4-mo1.0Fall / Spring1.0No — occupies drop slot only
Co-op 4-mo1.0Summer A0.5Yes — spans sumA → sumB
Internship 2-mo0.5Summer A0.5No — occupies one summer half

This arithmetic applies identically for any institution's work terms — adding an exchange semester at a new school just requires adding a duration descriptor with the appropriate weight.

Extensibility — what you can change without touching core

The architecture makes a deliberate promise: each dimension of institution-specific behavior is owned by exactly one adapter file. Changing it requires no knowledge of how the rest of the app works.

What you want to changeEdit onlyWhat happens automatically
Add a trimester / quarter structureadapters/northeastern/calendar.js — change getSemesterTypes()Semester grid rebuilds. Span arithmetic adjusts. Year headers update. No core changes.
Add a new gen-ed framework codeadapters/northeastern/attributeSystem.js — add entry to _attributes and _gridLayoutGradPanel grid gains the new cell. getCoverage() starts tracking it. No UI changes.

Add a new themeAdd an entry to src/core/themes.js THEMES mapThemeContext + Header cycle button pick it up. No other changes.

Forking for a new institution — four steps

  1. Copy the adapter folder: cp -r src/adapters/northeastern/ src/adapters/myuniversity/
  2. Edit adapter files: At minimum, institution.js (identity and storage prefix) and courseCatalog.js (data URL + normalization). Edit others as needed for your semester structure, gen-ed system, and work terms.
  3. Change src/config.js: Replace line 2. That's the only non-adapter file that needs to change.
  4. Add course data: Place your JSON at the path set in courseCatalog.js. The adapter owns the fetch strategy — the rest of the app receives a normalized Course[] regardless of source.
