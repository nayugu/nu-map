This is the reasoning behind NU Map that you cannot recover by reading the code. It is not an architecture tour and not a setup guide; it assumes you can read the codebase yourself. What is here is the set of decisions that look arbitrary, or look improvable, until you know what they cost, plus the assumptions the code quietly depends on. Its companions: FORK.md for the legal and identity side of taking this over, CLAUDE.md for how to work in the repo day to day, and `docs/` for the design of record of each subsystem.

## 1. Non-obvious design decisions

**A student's plan never leaves their own browser.** Privacy is the first reason, and the point is that it is a property of the architecture rather than a promise in a document: there is no server to breach, subpoena, or misconfigure. Two things keep it right. There is almost nothing to depend on, so almost nothing to break, and cost scales with the size of the catalog rather than with the number of students. Accounts or sync would trade that away for convenience.

**Course ratings are published in batches, and the delay is what protects the people who submitted them.** Students can report a course's workload and difficulty. They are read from a static file recomputed on the data pipeline's schedule, and written blind, one anonymous submission at a time. The batch schedule is the actual privacy mechanism. A live average leaks individuals by subtraction: watch a course go from 7 ratings averaging 3.20 to 8 averaging 3.30, and you have the eighth person's exact answer. Recomputing on a schedule collapses the timing so there is nothing to subtract. Making the average live would look like a pure improvement and would de-anonymize every rating.

**The share code is the key to the plan, so our own relay cannot read what it is holding.** Sharing by code parks a plan on a server briefly so another browser can collect it. The server used to generate the code and could decode the plan, which made "we don't read your plan" rest on our good behavior. Now the browser generates the code and derives two things from it: the address to store the plan at, and the key to encrypt it with. The server sees only the address and the ciphertext. Both come from one deliberately slow computation, because the server is handed the address: were it a fast hash, the server could try every possible code until one matched, and the key would fall out with it.

**If the app states something, it has to be true, so it says less rather than guessing.** A corequisite sentence that offers a choice is dropped whole rather than read as a list of required courses. Class-standing rules that disagree across a course's sections produce no rule at all. The asymmetry is the reason: a constraint we invent refuses a plan the student is actually allowed to take, while a constraint we miss only schedules a course earlier than it had to be. Prefer less information to wrong information, and say so on the surface wherever we are unsure. It is also how I rank bugs. The dangerous ones are the ones we cannot surface, where the tool believes it is right and has no way to find out otherwise.

**The plan generator decides when you take a requirement, never which course you use to satisfy it.** Roughly half of a degree is a genuine choice, so an engine that picked for you would be inventing your degree rather than scheduling it. It emits reservations: unfilled slots that sit in a semester carrying the requirement's own name, which the student then fills. This is the first thing someone will want to relax, because filling the slots in looks more helpful right up until it is wrong. For the same reason, the rules about what makes one schedule better than another are a ranked list with tolerances ("co-op depth first, then early breadth") rather than a weighted score. Any weighting is invented, and invented numbers end up defended as though they were measured.

**The verification badge means we copied the catalog correctly, not that the catalog is correct.** It is also not a cross-check against a second system, because for degree requirements no second system exists: Degree Works and the CourseLeaf admin need a login, Banner publishes no program data, and the printable PDF is the same page. That has been checked; do not hunt for it again. There are three verdicts rather than a pass and a fail, because "needs review" has to mean we can point at evidence, while "partly checked" means nothing looks wrong but a check could not run. Each program is judged against the checks that make sense for its kind, so a minor is not marked down for lacking a four-year plan minors never publish.

**Every fact has one trusted source, and which source is trusted depends on the fact.** NUPath (Northeastern's general-education requirements) is authoritative on the Registrar's public dashboard; course titles, descriptions, and prerequisites are authoritative in the catalog. Two rules keep the merge honest. A source may only delete a value it is capable of stating in the first place: the catalog can print 11 of the 13 NUPath codes and never prints two of them, so its silence about those two means nothing. And only the trusted source for a field may delete at all; the others can add. A single ranking of "best source" is tidier to write and quietly deletes real data.

**Where reading the catalog takes a human judgement, a human makes it, and the scraper stops rather than guessing.** A few things on the page cannot be settled by parsing: whether a second requirements table is a variant of the same program or a different program, whether a list of courses is a requirement or a menu that some other requirement points at. Those live in small hand-maintained tables, and a case the table does not recognize fails the whole scrape. That hard stop is the design, not a gap in it. Both obvious classifiers were built and measured before being thrown away: one misfiled eight real program variants, the other disagreed on 16 of 45 pages and called a program's sequential phases alternatives. Where Northeastern states something in a convention it follows consistently, that gets a rule instead, since a hand-maintained list of facts goes stale silently every year.

**What you must complete is frozen at the catalog year you started under; everything else is today's.** Northeastern publishes a new catalog each academic year and a student's requirements are locked to the one they entered under, which is why the app ships several years of programs at once. This split governs the entire data layer and it is not uniform, and treating it as uniform produced two contradictory designs before it was written down. Requirements come from the entry year, because that is what the university enforces. Whether you can register next spring comes from today's prerequisites and offerings, because that is what the registrar checks. Older catalog years are kept only to answer whether a course existed and what it was called.

**Everything specific to Northeastern is isolated behind one layer, because Northeastern keeps changing its systems.** They moved to Banner only recently and are already trialling something else, and the catalog's page markup changes without warning. A change appears in a scrape immediately; whether we read it correctly is a separate question, and I have only ever heard about backend changes by talking to advisors, never from any announcement. So that boundary is not there to satisfy a design pattern. It is there so that replacing a data source is a new adapter instead of a rewrite, and so that pointing this at another university stays possible.

**The public data pages are ordinary web pages first, readable by a person or an AI.** They double as a plain catalog site, which is useful on its own. There is JSON underneath, but the pages are the real interface: most AI tools will only fetch a link they have already seen, never a URL they construct, so every page has to be reachable by following links from the last one.

**The license is a shield, not a business model.** AGPL means anyone who runs a modified copy as a website has to publish their changes, and the paid commercial option exists so that a company cannot take the scrapers and the requirements parsing closed while we keep maintaining them for free. Neither half is a plan to make money; both exist so the values travel with the code. The copyright deliberately does not transfer in a handoff, because holding it is the only thing that keeps that option alive.

## 2. Invariants and things not to break

- **Nothing about a plan reaches a server unless the student asks, every time.** There are three ways out, all optional and all per-use: the Claude integration, a share link (which encodes the plan into the link and touches no server of ours), and a share code. A fourth way out is a new promise, and it belongs on the privacy page before it ships.
- **Grades never leave the browser**, not in a share link, an export file, or anything sent to Claude. The plan registry marks them private, and the privacy page states it as a commitment.
- **A course with no grade entered counts as passed.** The assumption is applied inside the evaluators only, never saved, displayed, or shared. That is what keeps grades purely additive: with none entered, the app behaves exactly as it did before the feature existed.
- **Claude proposes; only the student applies.** Make trusted actions automatic and a model can quietly rearrange someone's degree.
- **A new field on a plan is registered in one place, or it silently disappears.** A plan is written out in four places (the browser's storage, a share link, an export file, the snapshot sent to Claude), and the registry that lists its fields exists because each of those had separately lost one. Add the field to the registry, never to the four.
- **The short keys inside a share link can never be renamed or reused.** A link is a compressed, encoded copy of the plan with no version number in it, so that key map can only ever be added to. Change one and every link anyone has ever sent decodes into the wrong fields, with nothing to detect it.
- **The save-on-close path must read the live plan, not a copy.** It once watched 12 fields while the save routine wrote 26, so a stale copy overwrote 15 things a student had set. It looked like "it didn't save" rather than like a wipe, which is why it survived so long.
- **An unfilled slot takes up room in a semester without ticking off a requirement.** It counts toward how many seats are taken, never toward how many are answered.
- **Any check that recognizes a program by its catalog year or its web address goes silent exactly when it matters.** The check that stops program quality regressing skipped every program on the first scrape of a new catalog year, because the year is part of the name it looks up, and two others went quiet when Northeastern renamed all 26 Data Science programs to Artificial Intelligence. Ask of any new check what it does on the first run after a rename.
- **Never weaken a safety check to make a failing data run publish.** The scrapers hold a whole run in memory and refuse to write when the result looks like the catalog broke rather than changed. A check that fires is the system working.
- **"We never asked", "we asked and got nothing", and "the answer was no" are three different facts.** A term we never read is not a term the course was missing from, and a catalog page that timed out is not a discontinued subject. Every scrape bug of consequence here has been one of these collapsing into another. The same holds for what we print: an empty result is shown with its denominator, because a section left out looks identical to a check that never ran.
- **A course Northeastern has retired stays in the app while any published catalog year still requires it**, and the build refuses to ship a program whose courses it cannot find. That check names the missing courses rather than counting them, because a count of three passes while three different courses go missing.
- **Fix bad data in the scraper, never in the data.** Anything else is overwritten by the next scheduled run. There are two scrapers, undergraduate and graduate, so a fix applied to one is the normal way to half-fix something.
- **Never hard-code a date, a year, or the boundary of a semester.** When the current term starts, which catalog year is current, and what year a new student defaults to are all derived. Every hand-picked value here has eventually gone wrong, quietly.
- **The PDF export is English on purpose**, so do not "fix" it. Every other user-facing string exists in all eight languages, which makes an English sentence written directly into a component always a bug.
- **The "not affiliated with Northeastern" notice comes before anyone can plan.** We are not affiliated with Northeastern. That is the whole reason.
